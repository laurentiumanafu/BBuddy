## The pipeline as it now stands

```
<wow>\Data\data                       the client's own store, no CDN needed
      |  cascdump      extracts root ADTs, solves each tile from MDDF/MODF
      v                     or from the MCNK chunk position
  <map>_<x>_<y>.adt
      |  navbake bakeall           -> .navtile (268x268 heights, 1.99 yd cells)
      v
      |  mmapbuild --map 1         -> <game>\mmaps\*.mmtile + 001.mmap
      v
  Navigation.dll reads <dll dir>\mmaps   <- it is next to CopilotBuddy.exe
      |  RouteRunner -> Tripper.Navigator.FindPath
      v
  ClickAim walks the returned polyline point by point
```

One command runs all of it on Windows:

```bat
Tools\build-navmesh.cmd "C:\Games\WoW" 1 -614.8,-4254.2,39 "C:\BBuddy"
```

## What is proven, and how

* **x64 DLL**: PE32+ `0x8664`, 116 exports, all 74 P/Invoke entry points present,
  imports only KERNEL32 + ucrt. `Tools/Navigation/check_pe.py` re-checks it.
* **mmaps load and route**: on a two-ADT synthetic map with a wall, Detour returns
  `status 0x40000000`, 269 polys, 451.5 yd around the wall vs 330 yd straight, through
  the gap at x = -267. Seams are genuinely linked; a straight line would mean the
  tiles were never joined.
* **the extractor parses its formats**: `make -C Tools/CascAdt test` builds a synthetic
  CASC store (both `.idx` layouts, multi-frame BLTE, stored and zlib frames, two
  continents claiming the same tile, a chunk-position-only tile, a tile with no
  position data, a WDT lookalike, a zero-length span entry) and asserts the output.
* **end to end**: that store -> `cascdump` -> `navbake` -> `mmapbuild` -> `mmapcheck`
  answers a real path query, and `navbake probe` reports the exact height that was
  put into the fixture.

Not proven: anything running on Windows against the real 70291 data. The DLL has never
been loaded by CopilotBuddy, and `cascdump` has never seen a real store.

## The first thing to do next

1. `cascdump list --data "<wow>\Data\data"` — expect hundreds of thousands of entries.
   A handful means the wrong folder; zero means no `.idx` there.
2. `cascdump dump ... --ref <player x,y,z>` — expect thousands of ADTs and very few
   `unknown_*.adt`. The height printed for the tile you are standing on must match the
   Z the bot logs; if it does not, the tile axis convention is mirrored for this build
   and `tile_of_world()` in `cascdump.c` is the one function to flip.
3. `build-navmesh.cmd` with the same reference point.
4. Launch, look for `[NavMesh] Navigation.dll loaded: yes ... N tile files` in the log.

## Known limits, in the order they will bite

1. **Continent identity.** Tile (32,32) exists on Kalimdor and on Eastern Kingdoms; the
   store does not say which is which. The first one found keeps the plain name, the
   other goes to `alternates/` with its EKey, and `--ref` prints both heights. For the
   area around the player this is enough (the tile the player stands on is decided by
   the height match). For a whole continent it is not: the fix is a growth pass that
   clusters tiles by shared-edge heights, which is not written yet.
2. **Terrain only.** No `_obj0` doodads, no WMO buildings, no cave interiors, no
   liquids. Buildings will be walkable-through in the mesh. `LiveMesh`-style runtime
   raycasting (option A in `hunt/NAVMESH_PLAN.md`) is the upgrade path.
3. **Mobs, transports, Z-dependent hotspots** are untouched by any of this.
4. **`GeneratePath` is unusable on x64** (`ObjectManager.Me` is null), which is why
   `RouteRunner` drives `Tripper.Navigation.Navigator` directly.
