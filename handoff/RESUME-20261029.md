## The pipeline as it now stands

```
<wow>\Data\data                       the client's own store, no CDN needed
      |  cascdump      extracts root ADTs, solves each tile from MDDF/MODF
      v                     or from the MCNK chunk position
  <map>_<x>_<y>.adt
      |  navbake bakeall           -> .navtile (268x268 heights, 1.99 yd cells)
      v
      |  mmapbuild --map 1         -> <game>\mmaps\*.mmtile + 001.mmap
      v
  Navigation.dll reads <dll dir>\mmaps   <- it is next to CopilotBuddy.exe
      |  RouteRunner -> Tripper.Navigator.FindPath
      v
  ClickAim walks the returned polyline point by point
```

One command runs all of it on Windows:

```bat
Tools\build-navmesh.cmd "C:\Games\WoW" 1 -614.8,-4254.2,39 "C:\BBuddy"
```

## The second route, which does not need the store at all

The first route depends on reading build 70291's CASC index. The repack that ships
next to the client already carries the same terrain in the server's format, and that
format is documented in the server source:

```
<repack>\data\maps\0013232.map    129x129 heights + 16x16 hole mask, per tile
      |  mapdump convert                Tools/MapFiles
      v
  <TEMP>\1_32_32.navtile
      |  mmapbuild --map 1              Tools/NavMeshBuilder
      v
  <game>\mmaps\0013232.mmtile
```

```bat
Tools\MapFiles\maps-to-mmaps.cmd "B:\World of Warcraft\ForeverRepack\data" 1 C:\BBuddy
```

Same mesh format, same DLL, same `RouteRunner`. Terrain (hills, cliffs, holes,
shorelines) is real; buildings and bridges live in `vmaps` and are not included. It
converts a whole continent in about a minute and produces real mmaps **today**,
without waiting for the CASC index to be solved.

If both routes work, prefer this one for continents and the CASC one only if the
repack's map files turn out to be a different client build than 70291.

## The three tile numbers (this costs a day if it is wrong)

| number | formula | where it appears |
| --- | --- | --- |
| blob index (`dtMeshHeader::x/y`) | `floor(32 + centre/533.33)` | what Detour uses: `calcTileLoc`, every query, the on-demand loader |
| grid / file number | `floor(32 - centre/533.33)` = **`63 - blobIndex`** | `<map><x><y>.mmtile`, `.map` names, `WorldToTile` |
| this build's 4x4 sub-tile | 16 blobs per file, `127..130` for ADT 32 | our own `mmapbuild` output only |

vmangos has both halves in the source: `TileWorker.cpp` derives `params.tileX` from
`(bmin+bmax)/2 - orig`, `MapBuilder.cpp` writes the file as `%03u%02u%02u` from
`bmax[0] = (32 - tileX)*GRID`. Tile 32 is where they almost coincide, so a mirrored
name hides until the second tile. `legacyfixture` mirrors the name on purpose and
`test_legacy_mmaps.py` asserts the name the loader derives is a file that exists.

## Using the mmaps you already have

`Lib\x64\Navigation.dll` resolves `mmaps\` **next to itself**, so an existing set only
has to be reachable from there:

```bat
Tools\UseExistingMmaps.cmd "B:\World of Warcraft" C:\BBuddy
```

It finds the folder that holds `*.mmap`, reports how many tile files of each naming
scheme it sees, creates a junction beside every `Navigation.dll` under the target
folder, and then loads every tile of the first map through `mmapcheck.exe` so a
rejected set shows up at the console instead of in the game log. Nothing is copied.

Two rules:
* **never mix** our own 4x4 output with a stock set in one folder - the tile size in
  `<map>.mmap` (133.33 vs 533.33 yd) has to match every tile beside it;
* the file that has to exist is `<map>.mmap` (001 or 0001) - tiles without it are
  never opened, because `dtNavMesh` is initialised from those params.

Then look for `[NavMesh] Navigation.dll loaded: yes` in the bot log, and walk
somewhere with a wall between start and goal: the path must bend around it. A straight
line means the mesh was not used (grid fallback), not that the mesh is fine.

## What is proven, and how

* **x64 DLL**: PE32+ `0x8664`, 116 exports, all 74 P/Invoke entry points present,
  imports only KERNEL32 + ucrt. `Tools/Navigation/check_pe.py` re-checks it.
* **stock mmaps load and route** (`python3 Tools/NavMeshBuilder/test_legacy_mmaps.py`,
  18 checks, 0 failed): a real 533 yd tile written in the server container is accepted
  with a 16- and with a 20-byte header, routes 460.7 yd around a wall where the straight
  line is 400 yd (so the doorway is really used), stops at the wall with Detour's
  partial result when the doorway is removed, is refused when the blob was built for
  another Detour version, and is refused without a blind read when the size field
  overruns the file. The same store renamed to `0001.mmap` / `0001_32_32.mmtile` works.
* **mmaps load and route**: on a two-ADT synthetic map with a wall, Detour returns
  `status 0x40000000`, 269 polys, 451.5 yd around the wall vs 330 yd straight, through
  the gap at x = -267. Seams are genuinely linked; a straight line would mean the
  tiles were never joined.
* **the extractor parses its formats**: `make -C Tools/CascAdt test` builds a synthetic
  CASC store (both `.idx` layouts, multi-frame BLTE, stored and zlib frames, two
  continents claiming the same tile, a chunk-position-only tile, a tile with no
  position data, a WDT lookalike, a zero-length span entry) and asserts the output.
* **end to end**: that store -> `cascdump` -> `navbake` -> `mmapbuild` -> `mmapcheck`
  answers a real path query, and `navbake probe` reports the exact height that was
  put into the fixture.

Not proven: anything running on Windows against the real data. The DLL has never been
loaded by CopilotBuddy, and `cascdump` has never seen a real store.

## Known limits, in the order they will bite

1. **Continent identity.** Tile (32,32) exists on Kalimdor and on Eastern Kingdoms; the
   store does not say which is which. The first one found keeps the plain name, the
   other goes to `alternates/` with its EKey, and `--ref` prints both heights. For the
   area around the player this is enough (the tile the player stands on is decided by
   the height match). For a whole continent it is not: the fix is a growth pass that
   clusters tiles by shared-edge heights, which is not written yet.
2. **Terrain only.** No `_obj0` doodads, no WMO buildings, no cave interiors, no
   liquids. Buildings will be walkable-through in the mesh. `LiveMesh`-style runtime
   raycasting (option A in `hunt/NAVMESH_PLAN.md`) is the upgrade path.
3. **Mobs, transports, Z-dependent hotspots** are untouched by any of this.
4. **`GeneratePath` is unusable on x64** (`ObjectManager.Me` is null), which is why
   `RouteRunner` drives `Tripper.Navigation.Navigator` directly.
