# Experimental gameplay: build 70707

Build 70707 is discovered on normal startup; no special launch argument is needed. Builds 70291 and 12340 retain their separate paths. No Lua is used.

## Supervised expanded mode

Continuous Grind and GatherBuddy are enabled experimentally, using a profile or profile-free mesh roaming. Grind may use the configured rotation, healing, buffs, food/drink, looting, optional gathering and registered-merchant selling. GatherBuddy uses the configured professions and skill levels. These are existing feature paths, not a claim that they have all been verified on 70707. Settings still control which features run.

When self-buffs are enabled in Combat Settings, both Grind and GatherBuddy attempt recognized hotbar buff actions on a fresh run and after confirmed resurrection. Attempts wait for a quiet point outside combat and outside gathering interactions; long route legs, combat and rest can delay them. They select self using the default F1 binding and verify the selection, leaving normal target acquisition to choose the next mob. On 70707, attempts are deferred while the candidate mana value is zero; exact spell costs are unknown.

After the initial attempt, 70707 **experimentally** reads the observed inline aura candidates for Frost Armor ID 168 and Arcane Intellect ID 1459 only: it holds refresh while the candidate has more than 30 seconds remaining, and attempts missing or nearly expired candidates at the next quiet opportunity, with at least 30 seconds between attempts. `[Buff] 70707 experimental aura candidate` logs status transitions and approximate remaining time. One Mage session supports the ID/timing interpretation, not all characters, a complete aura model or cast success. If the candidate layout, timing or reads are unknown or unstable, the original 30-minute key-attempt timer is used; all other spells and 70291 always use that fallback. Thus a failed cast can still remain unbuffed until the next fallback attempt, and buffs with a shorter duration can expire early. Implicit druid forms and known passive racials are excluded; explicit role overrides remain user choices. The first 12 action slots and their default key bindings are assumed. No Lua is used.

1. Build x64 and attach to the logged-in 70707 client. Confirm your real action-key bindings, including F1 and TAB, and your food/drink slots. The first 12 candidate action slots are read; the bar must be nonempty and stay unchanged during the run. The client memory does not prove that the keys are bound as assumed.
2. In Combat Settings select **Allow** and enter known eligible IDs, or select **Blacklist** and enter IDs to exclude. Blacklist permits every other readable key, including potentially friendly NPCs; supervise closely. The observed Trogg key was 36; it is not added automatically. The selection-free nearby scan works while stopped. A faction key does not establish hostility or merchant status. No target needs to be selected at startup. Unknown keys and NPCs blocked by the selected filter are withheld, including in defence, because attacker identity is still unknown.
3. Configure the mesh, profile or profile-free roaming, and any desired combat, gather and selling settings. For selling, stop the bot, record a town location and explicitly select/record a merchant, then record the user-confirmed selling click plan. Selling replays coordinates; it does not verify that the merchant window opened, the inventory state, or that items sold. The full-bag/item reader and automatic merchant-type detection remain unresolved.
4. Watch the character and use STOP immediately if anything is wrong. STOP releases held movement and revokes experimental reads, but cannot guarantee the game's already-enabled auto-attack is off; check it manually. Healing uses F1 and TAB to retarget; auto-attack may persist when the target changes. A selection/allowlist check before the next bot attack cannot prevent a client-side auto-attack already active during retargeting. Avoid friendly NPCs and manually intervene if needed.

For 70707 Grind, if the drink percentage is nonzero, voluntary pulls wait until mana reaches that value even when no drink is present or a hotbar press fails. Defence, STOP and an explicitly requested vendor trip take priority. This recovery gate is currently 70707-only because the 70291 active power type is not verified; it is not applied to rage or energy. The normal food/drink wait limit does not cap passive recovery.

Startup checks partial build signatures, candidate map and living player, the active faction filter and stable action bar. A statically supported, once-observed local ghost-flag candidate at `unit+0x26D8 & 0x10` is a conservative veto: startup is refused, or a running session stops, if it is set, unstable or unreadable. An unset bit does not prove life and does not authorize corpse recovery. At least two of four code anchors must match and any readable mismatch is rejected; inaccessible anchors are reported, not treated as mismatches. Gameplay reads are bound to the startup/worker thread and revoked on STOP, failed starts, and worker exit. Reads and input are non-atomic. The combat flag, health-zero/death interpretation, faction, power, movement and other fields remain candidates; currently only the observed mana-type-0 power interpretation is enabled. Unlisted attacker defence is not implemented. Other legacy bot modes and standalone route-only profiles are not automatically made compatible by this experiment.

The 70707 game-object vtable candidate `0x41E1480` was found by static comparison (14 matching-function votes). The latest log shows matching-layout node candidates, but does not prove the full semantics. A build-specific mouseover candidate `0x51C7A78` is now used instead of the unrelated 70291 address; it has static cross-build support but no live hover validation. A full matching GUID, a fresh eligible nearby node, and existing cursor, combat and STOP checks are still required before right-clicking. The user reports successful background gathering; this does not independently validate the candidate fields or all client conditions. The scanner retains GUID, back-pointer, entry, profession and skill checks, so it may reject real nodes or find none; no correct harvest is implied. The 70291 candidate remains separate. Optional Grind gathering considers resources within 25 yd before chasing distant pulls: combat, any living or unreadable NPC within 12 yd, and eligible or unreadable pulls within 40 yd block the detour. These are conservative proximity heuristics, not hostility detection, and are rechecked during movement and interaction. The scan reports known GUID-entry candidates and header rejections to help diagnose missing nodes.

Gather search remembers the last matched ore pixel as well as the existing herb pixel within a session and tries the appropriate hint first. This is only a search-order optimization: hints can be stale after camera or window changes and never authorize a click; the full search and checks remain. The six-second stillness window remains because gather-cast completion is not yet validated. World coordinates alone do not identify a safe screen pixel, and the legacy 32-bit object-interaction method is not established for this client.

A background test showed a clear posted away/return transition and 60/60 matching hover samples while the desktop mouse moved in 60/60 samples; an earlier test had zero movement and was inconclusive. The user subsequently reported that actual background gathering worked while moving and clicking the desktop mouse. These observations are not a guarantee: input timing, overlays, focus changes, camera motion and client versions can differ.

GatherBuddy and optional Grind gathering now always allow desktop mouse movement when another application has focus; the old checkbox has been removed and a saved `AllowBackgroundCursorMovement=False` is ignored. With WoW in the foreground the bot still checks whether the real cursor or a mouse button disrupts the hover; if no button-down was sent, it waits 150 ms, refreshes the node and retries with a new cursor baseline rather than waiting six seconds and cooling the node down. Repeated interruptions yield to the normal combat/STOP loop and the node can be reconsidered. A posted button-down still triggers the normal six-second cast/loot wait, including if the button-up post fails. In both modes the game must be non-minimized with a known focus state and unchanged client geometry. Focus changes discard the search and retry; unavailable focus/geometry fails closed. Away-to-node GUID transition, node eligibility, fresh nearby node, combat, extra Grind safety, STOP, client identity and final matching hover checks remain. Reads are not atomic and focus or hover can change between the last check and the click. A manual cast coinciding with a cursor-only retry cannot be reliably detected. No native object interaction or click-without-hover is enabled.

An opt-in **ClickAim Tools → Gather background test** can investigate without starting a bot: stop the bot, start the test, focus the game and hover a visible nearby node within eight seconds, then switch to another application and move the desktop mouse while leaving the character, camera and game window untouched. The test posts only away/return mouse-move messages, then samples hover and desktop movement for six seconds. The log reports the away/return transition and counts; a matching candidate is classified by GUID entry only, not proven to be the node. Switching between non-game foreground applications is allowed; brief periods with an unavailable foreground during sampling are skipped (bounded to 20 samples) and reported. The test discards the result with a specific reason if the game regains focus, minimizes or moves, its client changes size, the attachment or stop state changes, or a required read fails. If switching away minimizes WoW, try windowed or borderless mode. Zero movement is inconclusive; other applications, occlusion, game behavior, timing and non-atomic observations also limit the result. It does not itself click or change gathering settings.

## Evidence and diagnostics

The user observed successful 70707 killing and looting. Two supervised fight logs showed target candidate health 55→40→25→10 and 55→39→24→9, and player mana 171→156→141→126. A later log recorded corpse interactions, but those do not independently verify the resulting inventory changes. The candidate action slots 1–3 matched Attack 6603, Lightning Bolt 403 and Healing Wave 331. Nearest mesh polygons were 0.18 and 0.20 yards from player and target; that query did not itself validate a route.

`[70707 candidates]` logs candidate GUIDs, player name, pointers, map and camera zoom. Player and selected-record logs include candidate raw health, level, faction and power; `[70707 action research]` prints the first twelve candidate qwords. These can contain identifying information and process addresses. Synthetic tests and static comparisons are not a Windows build or a live game test.

The client must be x64 and its version resource readable. Discovery includes `Wow`, `Luacct`, `WowB` and `Wow-decoded`; `/pid=1234` can select a differently named process by its actual PID.
