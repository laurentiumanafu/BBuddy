# WowB death and corpse recovery investigation

**Experimental automatic recovery is enabled only for 70707 Grind and standalone Gather.** After a zero-health checkpoint made in the current running session, the worker unwinds any combat or route call before attempting a single Release Spirit click, a mesh-only ghost route toward the candidate location, a search for a safer resurrection position, and a single Accept click. It resumes only after two positive-health, ghost-bit-clear observations and the action-bar session guard. These are experimental candidates, not proof of death, a corpse, a ghost or a successful resurrection. The 70291 and 12340 paths are unchanged and do not use this recovery flow.

STOP, loss of attachment/session, a changed player GUID or map, a missing or unstable ghost flag, missing mesh, an incomplete path, excessive distance or failure to confirm a transition stops recovery. Only the in-memory checkpoint from this run is used; saved files are not reloaded. A user STOP is never cleared to start or resume recovery. The death candidate requires the same full player GUID and map observed alive within the previous 30 seconds; health and identity are sampled twice at zero, with map and attachment rechecked. A file is written to `Logs/CorpseRecovery/` for each candidate and may contain identifying data. Both state and position reads are non-atomic; rapid release, unreadable death fields, a blocking action or wrong candidate data can prevent capture or make the location wrong. Starting dead or as a ghost does not provide a checkpoint and cannot start this recovery.

Each UI action requires an English dialog at the supplied native glyph size. With WoW foreground, the worker captures visible client pixels and retains the physical-cursor-still guard. With a different application foreground, it experimentally asks Windows `PrintWindow` for the game client instead; it never captures the unrelated foreground window as the game's UI. A background capture must show a button-region change after a posted hover before a click is allowed. Blank, static, stale-looking, minimized, cloaked, unreadable or timed-out captures fail closed; modern GPU games may not support this capture path at all. A hung background capture runs on at most one worker and does not block STOP. Foreground/background transitions and geometry changes discard the frame; physical desktop cursor movement is relaxed only while another application remains foreground.

The worker waits up to 45 seconds for each prompt. It requires uniquely matched labels on a red button, with the resurrection heading above Accept, plus the expected player state, same map/identity and, for Accept, proximity to the checkpoint. It sends a hover-away, checks the dialog again, sends a hover to the candidate button, rechecks the state, geometry and button and then posts one bounded click. After hover it checks up to four frames for a valid, fresh response; STOP and identity guards remain active. The user-supplied highlighted Release Spirit screenshot uses light glyphs with a red tint; the matching palette now includes this appearance in addition to yellow and white. The worker waits for the state transition without blindly repeating a sent click. UI overlays, focus, screenshots and game state are not atomic and a lookalike dialog is still possible. The ghost route stops if identity, map or ghost checks fail; it refuses straight-walk fallback, partial paths and incorrect mesh endpoint snaps. If the mesh or the session's already-calibrated route mover is unavailable, it stops before release rather than running the existing unguarded calibration walk during recovery or knowingly stranding the character. A 2026-11-03 Gather log recorded the NPC-aware flow end to end: it saw 10 non-player units, routed to a point logged as 32.0 yd from the checkpoint and 36.3 yd from the nearest observed unit, posted the Accept click, and confirmed its alive candidate/action bar before resuming. This is one observed run, not proof of general NPC safety or fully validated state offsets.

In the user's November 3 foreground attempt the checkpoint was saved and the bot repeatedly logged `dialog, state, cursor, focus or client geometry changed` without posting a button down. A subsequent background attempt logged post-hover match failures and once `background capture showed no fresh button response to hover`; no click was sent. In the supplied screenshot, the Release Spirit button is highlighted. Offline analysis confirmed the prior matcher misses that screenshot because the light glyphs are red-tinted; the revised palette matches both the original unhighlighted and this highlighted screenshot and rejects the highlighted screenshot with its label masked. Those positives are in-sample, and the screenshot is of the visible desktop, not the raw PrintWindow frame. The screenshot alone does not establish background-capture freshness or message delivery. The user later reported that recovery worked in their setup.

## Resurrection-position heuristic

The user reported successful recovery and that the resurrection prompt appears about 40–50 yd from the corpse. The ghost route now interrupts at approximately 35 yd from the saved position and scans the live object pool. It considers all observed non-player unit candidates as potential threats, including unreadable/dead candidates and friendly NPCs; it does not claim to identify hostility. It prefers the current location if the prompt is visible and every observed unit is at least 35 yd away. Otherwise it ranks 16 mesh points on each of four rings (32, 24, 16 and 8 yd from the saved candidate), favoring distance from the nearest observed NPC; it limits route attempts and refuses partial paths, long detours, non-ground areas and guessed terrain layers. It requires the actual position to be within 38 yd of the recorded location, a maximum 15 yd height difference, at least 30 yd from all observed NPC candidates, and a visible matching resurrection prompt. NPC position, player identity, ghost state, map, ground and prompt are checked again immediately before the click. If a unit approaches, it tries to rescout; if a safe-enough reachable prompt position or a fresh capture cannot be confirmed, it stops rather than resurrect beside an observed NPC.

**This is a heuristic, not a guarantee of safety.** Pool enumeration and positions are non-atomic and may omit nearby units, and other players, unrecognized threats, aggro ranges, wandering patrols, terrain hazards, PvP and faction are not proven. Prompt distance was reported in one workflow, not calibrated on all maps. The bot can later return to the dangerous area when it resumes its ordinary profile; no temporary death-area blacklist is implied. The screenshot match and ghost byte remain candidates.

In the same log a later Gather defence ended with a changed target and a global safety abort, with no new death checkpoint logged. Player health at that instant was not logged, so the reason for the selection change and whether it coincided with death are unknown. The 70707 fight now stops sending combat input on a target or vitals safety exit and gives the owning checkpoint tracker 21 bounded observations separated by 100 ms waits (up to two seconds of waiting plus read time) to observe death/ghost state before requesting the global abort. Only a valid same-session checkpoint can lead to recovery; if no transition is observed it still stops rather than attacking a different target. The STOP generation and all recovery guards remain in force. Direct zero-health exits in the fight also use this path. This change has synthetic coverage but awaits a live test.

70707 static examination of the decoded PE found the `UnitIsGhost` registration at handler RVA `0x1801D10`: its local-object branch tests byte `unit+0x26D8` bit `0x10` after a type-table check. A fallback branch uses a different pointer and bit. This is only a **static candidate**, not a validated ghost-state decoder. `UnitIsDead` handler RVA `0x17FFCB0` checks health at `+0x1E28` with other flag logic. `RepopMe` and `RetrieveCorpse` handlers exist at `0x1455EC0` and `0x1457A10`, but their internal calls have not been validated; no Lua or internal client functions are invoked.

## November 2 labeled observations

Three user-supplied 70707 traces have labels `alive`, `dead before releasing`, and `ghost after manually releasing`. They use the same full player identity, no selected target, and each completed 100 samples. Their sample-zero health candidate at `+0x1E28` was respectively **232, 0, 1**; max-health candidate `+0x1E30` was **232, 202, 202**. A separate word `+0x1BB8` also read 232, 0, 1, and the unknown word `+0x0110` read 0, 4, 4. None of these words changed within the respective recordings. These are three labeled static observations, not recorded transitions or independent proof of ghost state; in particular health 1 must not authorize movement or clicks. Reasons for the changed max-health value are unknown.

The supplied recordings say their window ended at `+0x23FF`: they were made with an earlier recorder and do **not** include `+0x26D8`. An absent value is not zero and these traces cannot confirm or refute the static ghost-byte hypothesis. Compare suitable recordings without exposing the player's GUID using `python Tools/compare_death_traces.py alive.txt dead.txt ghost.txt`; it checks matching identities and reports missing bytes as not recorded. The labels and paths must be supplied in that order. The files themselves still contain sensitive raw data.

The user subsequently confirmed the short `dead`-labeled trace was recorded **after Release Spirit, while a ghost**. The byte matches the static `UnitIsGhost` local-path prediction, but this is one short ghost observation, not proof of the field's general behavior. No recorded transition established when the bit flipped. The earlier `+0x0110` difference is not a reliable state marker: the later `alive` baseline also has 4. The 70707 session now checks this byte with stable local-player identity and two matching reads; a set or unavailable byte stops or denies gameplay. An unset byte is not proof of life; recovery now uses this candidate alongside other guarded checks, but it remains unvalidated. The recorder reports which check failed in future captures, while retaining the same discard guards; this cannot determine the cause of the already-finished short trace.

## Screenshot investigation and visual diagnostic

Two screenshots supplied by the user show an English-language release popup with a changing countdown and **Release Spirit** / **Recap** buttons, and a **Resurrect now?** popup with an **Accept** button. The user confirmed the latter appeared near their corpse. The screenshots alone do not show the full death-to-corpse route, distinguish every lookalike popup, or establish that a posted click lands on the intended control.

**ClickAim Tools → Corpse dialog test** is a stopped-bot, read-only visual experiment. It asks the user to focus the game within ten seconds, copies the foreground client area from the visible desktop to process memory, and discards it without saving a screenshot. It checks the same attachment, STOP generation, focus and client geometry before and after capture. It logs whether patterns derived from the English **Release Spirit** button text and **Resurrect now?** heading are present; it sends no keys, clicks, movement or Lua. It rejects unsupported client sizes and an off-screen client. An overlay or another window can obscure/change the captured pixels; pixels, focus and geometry are not atomic. Matching text is not dialog identity or permission to click. The test does not attempt background capture and cannot decide that the resurrection prompt comes from the corpse rather than another source.

The exact two input screenshots match their respective patterns and reject the other pattern; blacking out the relevant label in either screenshot yields no match. This is still an **in-sample** test: the glyph patterns were extracted from those same images. Synthetic blank, solid-overlay and pattern tests also passed. Offline rescaled versions of these screenshots often did not match, so the probe deliberately supports only the supplied native glyph size; UI scaling, font rendering, localization, DPI, color or display changes may produce false negatives. Missing match proves nothing, and an unrelated overlay could be a false positive. No screenshot or character identifying data is stored in the repository; only the tiny binary glyph masks are embedded in code. The recovery path now also uses these masks, plus a separate Accept-label mask, red-button checks, uniqueness and geometry checks; no UI match is proof of dialog identity.

## Remaining validation

The user confirmed both live diagnostic classifications and subsequently reported successful corpse recovery at their current UI settings. The updated highlighted-button matcher has been checked offline on the supplied screenshot, but the new NPC-aware spot selection and its interaction with mesh routing, prompt availability and moving units have **not** been tested end to end. Scaling, localization or rendering changes can prevent detection. The stopped-bot recorder still provides read-only 25-second memory traces for investigation; it never calls client functions or uses Lua. The experimental recovery path should be watched in game and its logs retained if a step fails.
